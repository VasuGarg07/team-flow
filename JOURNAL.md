### 21 October, 2026 | backend
- Decision: used pwdlib with Argon2 for password hashing. Rejected bcrypt (it silently ignores everything after 72 bytes), passlib (no longer maintained), and plain SHA-256 or MD5 (far too fast for passwords). Decision: removed POST /users and made POST /auth/register the only way to create a user, so there is no second door that creates users with weak or fake hashes. Decision: hashing lives in security.py, so the service does not know which algorithm is used.
- Built POST /auth/register. The service lowercases the email, checks that it is not used, hashes the password and saves the user. The answer never contains the password or the hash. Password length is 8 to 128 characters, and the long limit stops someone sending a huge password to slow the server.
- Checked the users table in psql: the hashes start with $argon2id$, and two users with the same password got different hashes, which is the salt at work.
- What I learned: hashing is one-way and encryption is two-way, so we hash because we never need the password back. A salt is random text per user, saved inside the hash string, that stops one cracked password from exposing everyone who shares it. Hashing is slow on purpose, which is why plain def endpoints are better than async def here.

### 21 October, 2026 | backend
- Decision: used pyjwt with HS256 and a single secret from .env. Rejected python-jose (less maintained) and RS256 (only needed when other services must verify tokens without being able to make them). Decision: login takes a JSON body and the token is read with HTTPBearer, instead of the OAuth2 form style, so it matches the rest of the API. Decision: authentication is a FastAPI dependency (get_current_user), not middleware, so only routes that ask for it are protected. Access tokens last 15 minutes, set in .env.
- Built POST /auth/login and GET /auth/me. Login gives the same 401 message for a wrong email and a wrong password, so attackers cannot find which emails exist. The token payload only has sub (user id as text) and exp. I decoded one without checking the signature and could read it, which showed me a JWT is signed, not encrypted.
- What broke: the login endpoint crashed with ResponseValidationError because the service returned a plain string while the endpoint promised a TokenResponse. FastAPI checks the response going out, as well as the request coming in. Also my real JWT secret ended up in .env.example. I caught it before committing and replaced it with a placeholder and a new secret.
- What I learned: stateless tokens cannot be cancelled one by one, so they must be short-lived and paired with a refresh token (Day 7). Always pass algorithms=[...] when decoding. A secret in a committed file counts as leaked.

### 22 October, 2026 | backend
- Decision: refresh tokens are stateless JWTs for now. Rejected database-backed refresh tokens because they need a new table, a migration and more logic, which is too much for one hour. The tradeoff is that logout only clears the cookie, so a copied refresh token still works until it expires. I wrote the full rotation and revocation design in the README and can build it as a weekend follow-up. Decision: added a type claim (access or refresh) to every token and check it when decoding, instead of using a second secret, so a long-lived refresh token cannot be used as an access token. Decision: the refresh token goes in an HttpOnly, SameSite=strict cookie limited to /auth, and the access token goes in the response body so the frontend keeps it in memory.
- Built POST /auth/refresh and DELETE /auth/logout. Refresh rotates the cookie by giving a new refresh token every time. I tested register, login, refresh and logout in order. After logout the old access token still worked until it expired, because the server keeps no list of tokens, so the frontend has to throw it away.
- What broke: refresh crashed with "operator does not exist: character varying = integer" because I looked the user up by email using the user id from the token. Fixed by using get_user_by_id. Also I hard-coded secure=False and 7 days in the cookie even though I had settings for them.
- What I learned: a cookie is identified by name, domain and path, so logout must delete it with the same path it was set with. HttpOnly stops scripts from stealing the cookie but not from using it while the page is open, and SameSite stops other sites from sending it. A site is the domain, not the port, so localhost:5173 and localhost:8000 are the same site.

- Decision: kept all tenants in shared tables and isolate data with a membership check, instead of a schema or database per tenant, because it is the simplest and the usual choice. The tradeoff is that one forgotten filter would leak data, so the check lives in one place and I tested it with two users. Creating a workspace saves the workspace and the OWNER membership in one transaction: flush gets the new id inside the transaction, and one commit makes both permanent, so there is never a workspace without an owner. - What broke: db.delete(Workspace) used the class instead of the object. WorkspaceMemberRole was not exported from app.models. The generated migration had None as the constraint name in downgrade, and Alembic had warned about it in a comment.

### 22 October, 2026 | backend
- Decision: authorization has two layers. A dependency factory, require_workspace_role, is the gate that answers "may this role call this endpoint at all", and the service holds the finer rules that depend on the target, like "an admin can only remove plain members". Rejected putting every rule in the gate because the gate runs before the target is loaded. Decision: a workspace has exactly one OWNER, made when it is created, and nobody can be given the OWNER role later. This avoids the last owner problem and stops privilege escalation, and the tradeoff is that ownership cannot be transferred yet. Decision: the role is not stored in the JWT. It is per workspace and can change, so a 15 minute token would show stale permissions, and I look up the membership on each request. Decision: only the owner changes roles, and admins can add and remove members only.
- Built the gate and four member endpoints (list, add by email, change role, remove). Wrote down a permission matrix first and checked every endpoint against it. Non-members get 404 and members without enough rights get 403. This is the first place I used BadRequestError (400) for a rule violation.
- What broke: the router called change_member_role but the service named it update_member_role, which only fails when the request runs. DELETE workspace still promised a response body but returned nothing. The service version of add_member ignored the role in the body, and update and remove did not handle a missing member.
- What I learned: authentication says who you are and authorization says what you may do, so being logged in is not enough (my own GET /users/{id} lets any logged-in user read any user). A dependency can take arguments only if I write a function that builds the dependency. The order of checks matters: request rules first, then lookups, then rules about the target.
