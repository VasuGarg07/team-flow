- Decision: added one composite index on tasks (project_id, status, created_at) and no others. The columns compared with equals come first and the sort column comes last, so Postgres reads the rows already in order and needs no separate sort step. Rejected indexing every column I filter on, because each index makes every INSERT and UPDATE do more work and takes space, and for these queries it gains nothing. I left the assignee filter without an index because it matched about 13% of the tasks, so the planner correctly prefers reading the whole table. - Seeded the 5,000 extra tasks with --bulk and ran EXPLAIN ANALYZE on four queries: the task list, tasks by assignee, projects by workspace and members by workspace. Added the index with a third migration and the same Index in the Task model, and the downgrade drops it by the same name. The task list went from a Seq Scan plus a Sort that removed 5,078 rows to an Index Scan Backward with no Sort. The time went from 0.581 ms to 0.038 ms and the cost from 178 to 13.6.
- What broke: I first wrote the migration file by hand without the revision and down_revision variables, so Alembic could not read it. I also first ran EXPLAIN on a primary key lookup, which was always fast, instead of the real task list query. Postgres guessed 892 members for a workspace that had 7 because its statistics were old.
- What I learned: cost is a score used to compare plans, not milliseconds, so it cannot be compared with the actual time. A large gap between guessed and actual rows means old statistics, and ANALYZE fixes it. The planner skips an index on a small table or when a big share of the rows match. Foreign key columns do not get an index by themselves, only primary keys and unique columns do. A query that returns few rows but removes thousands in the Filter line needs an index.
- Also checked the project with the 5,000 bulk tasks (1,500 open tasks match). Before: Seq Scan plus a top-N Sort, 0.679 ms. After: Index Scan Backward that reads only the first 20 entries, 0.087 ms. The index still helps when many rows match, because the query has LIMIT 20 and the index is already in created_at order, so Postgres can stop early.
